# Agent Notes —— 决策笔记

[AGENTS.md](AGENTS.md) 是本目录的代理规则；本文件规定**记什么、记在哪、长什么样**。

代码和文档能回答「现在是什么」，回答不了「当初为什么这样、否掉了什么」。Agent Note 只存后者：让每个新会话的 agent 拿到项目记忆，不要把你已经否决过的方案当成新点子重新提一遍。

## 布局与命名

每篇笔记放在 `{生命周期}/{分类}/yyyy-mm-dd-slug.md`，两个维度都编进路径。

**生命周期**（顶层目录）——笔记随状态在目录间移动：

- `proposed/`：提案，尚未落地或只落了一部分。
- `implemented/`：已交付的决策，并与实际代码保持同步。
- `rejected/`：讨论后否决的提案。

目录不预建：第一篇笔记落进哪里就建哪里。

**分类**（二级目录）是封闭集合，门禁拒绝其他目录名：

| 分类             | 覆盖范围                                                   |
| ---------------- | ---------------------------------------------------------- |
| `arch`           | 交付代码的结构决策：进程边界、模块职责、数据模型、领域类型 |
| `feature`        | 面向用户的新能力                                           |
| `bug-fix`        | 缺陷修复，以及这类坑为什么只能这么绕                       |
| `simplification` | 砍掉代码、行为或范围，且不换回新能力                       |
| `process`        | 代码之外的工具与流程：门禁、依赖、打包、发布               |
| `testing`        | 测试基础设施与测试策略                                     |

`refactor` 被有意排除：它与 `simplification` 重叠，判别标准都是「可观察行为是否改变」。

文件名用**英文 kebab-case**（工具链友好），中文标题写在正文 H1。日期取该主题**第一次被提出**的时间，以 git 历史为准。

## 什么时候要写

只有「代码、测试、现有文档都解释不了的决策理由」值得写，且**与代码改动在同一个 PR**。

豁免（不写）：改样式、调 i18n 文案、局部 UI 微调、单点 bug 修——除非这个 bug 的成因值得下次避开。

- 决策已做、代码已写 → `implemented/`
- 想先写清楚再动手 → `proposed/`，代码落地时在同一个变更里改写成 `implemented/`
- 讨论后放弃 → `rejected/`，只在它还能拦住一个诱人的错误时保留

已经有一篇笔记管着这个决策 → **改它**，不要新建重复记录。换决策就换一篇新的，并让新旧两篇互相链接；不要在新笔记里悄悄改写旧结论。

## 文件格式

前四行固定，门禁校验：

```markdown
# Agent Note: <中文标题>

Status: <implemented | proposed | rejected — 一句话原因>
```

`Status:` 必须与所在生命周期目录一致，且全文件只有这一行。只有 `rejected` 的状态行带内容——读者打开被否决的笔记，要的就是结论。

正文以 `## 背景` 开头，之后按生命周期取必需章节：

| 生命周期       | 必需章节                                                        |
| -------------- | --------------------------------------------------------------- |
| `proposed/`    | `## 背景`、`## 提案`、`## 放弃的方案`、`## 验收标准`、`## 风险` |
| `implemented/` | `## 背景`、`## 决策`、`## 放弃的方案`、`## 影响`                |
| `rejected/`    | `## 背景`、`## 提案`、`## 放弃的方案`                           |

- **`## 决策` 用现在时**，描述已交付的事实。代码搬家、改名、改默认值后，笔记在同一次改动里跟着改（只改事实，不改决策）。
- `implemented/` 里**禁止提案语气**：`## 提案`、`## 计划`、`## 迁移步骤`、`## 验收标准` 这些标题一律拒绝，另外还有「应该」「计划」「将来会」。允许 `## 验证`、`## 后续`、`## 相关`。
- **`## 放弃的方案`是硬要求**：写下当时还想过什么、为什么不要。缺了这段，下个会话的 agent 会把它当新方案再提一遍。只记录真实考虑过的方案，不补编；实在没记录过就写明「当时未记录」，并说清现在为什么这么选。
- 交叉引用用相对 Markdown 链接，不写「第 3 篇」这类编号——移动目录后链接依然有效，门禁也能查。

## 不设索引

活跃的 `生命周期/分类` 目录树就是清单：浏览目录，或直接搜仓库。**不要新增 `INDEX.md` 之类的集中索引**——每个加笔记的分支都会改同一个文件，冲突必然出现，而它记的全是别处已有的事实。

## 生命周期之间怎么移动

- `proposed/` → `implemented/`：状态行改成 `Status: implemented`，`## 提案` 改写成现在时的 `## 决策`，`## 验收标准` 与 `## 风险` 折进 `## 影响` 或 `## 验证`，计划换成实际交付的东西。门禁按目标目录的骨架校验，改不全就红。
- `proposed/` → `rejected/`：状态行加一句原因，正文冻结。

个人项目不设归档层：笔记过时就在原处更新，决策被取代就写新的并与旧的互链。唯一该整篇删除的情况是 `rejected/` 里那个方案早就不可能再被提起。
